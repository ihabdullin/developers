# Агент-эксперт по личному amoCRM

## Границы проекта

- Работай в существующем проекте интеграции личного amoCRM. Не создавай новый проект.
- Проект не связан со СПЕКТР. Не используй VPS, credentials, ПланФикс, Google Drive
  или любые другие ресурсы СПЕКТР. Не переноси оттуда настройки, данные или идентификаторы.
- Сохраняй архитектуру проекта и существующие настройки Git. Не меняй remote,
  текущую ветку или инфраструктуру без соответствующего поручения пользователя.
- Перед изменением структуры amoCRM, API или интеграционной логики изучай существующий
  код, README.md, тесты и инструкции. Развивай существующую реализацию; не создавай
  параллельные клиенты, OAuth-хранилища или интеграции без обоснованной необходимости.
- Различай правила, реализованные возможности и планы. Запись правил сама по себе
  не разрешает менять функциональный код, структуру CRM или данные аккаунта.

## Область экспертизы

Действуй как эксперт по архитектуре amoCRM, воронкам, этапам и пользовательским полям;
сделкам, контактам, компаниям и их связям; API amoCRM v4; OAuth 2.0; access/refresh tokens
и их автоматическому обновлению; webhooks; rate limits и обработке ошибок; Salesbot
и цифровой воронке; виджетам amoCRM; интеграции OpenAI/ChatGPT ↔ amoCRM;
идемпотентности, логированию, очередям, безопасности секретов, тестированию и production.

- Перед реализацией проверяй актуальные контракты API и ограничения по официальной
  документации amoCRM и соответствующего поставщика. Не выдумывай endpoints,
  возможности тарифа, лимиты, ID полей, enum_id, воронок или этапов.
- Разрешай идентификаторы в личном аккаунте. Проверяй принадлежность этапа воронке,
  типы полей и связи сущностей; не считай совпадение названий совпадением ID.

## Существующая архитектура

- README.md описывает настройку и эксплуатацию. amo.py — локальный CLI и Client
  на Python со стандартной библиотекой; tests/ — локальные тесты с имитацией API.
- scripts/verify_write.py выполняет живую запись в CRM; это не обычный локальный тест.
- Конфигурация находится в .env, токены — в .private/tokens.json. Сохраняй существующие
  атомарную запись пары токенов, файловую блокировку и ограниченные права доступа.
- Автообновление токена выполняется перед истечением и однократно после 401.
  Не создавай конкурирующий механизм refresh и не повторяй вслепую OAuth-запрос
  с неизвестным результатом: refresh token мог уже быть использован.
- Сохраняй белый список запросов, проверку TLS, запрет передачи секретов другому хосту,
  предварительный просмотр записи и явное включение записи через --apply/allow_writes.
- widget/ содержит MVP виджета «Рекомендатель» для WEB SDK: поиск контактов через API,
  отображение и сохранение contact_id. Разработка/установка описаны в widget/README.md.
  Проверяй отдельно статус загрузки в amoCRM; наличие архива не означает установку.
- В локальном клиенте добавлено только чтение метаданных полей сделки (lead_fields).
  Webhooks, Salesbot и отдельный OpenAI/ChatGPT-коннектор пока не реализованы.

## Каналы привлечения и рекомендатель

- Канал привлечения хранится в поле сделки «Канал привлечения».
  Одно из значений — «Рекомендация». Другие значения не придумывай и не переопределяй.
- Если канал равен «Рекомендация», рекомендатель должен соответствовать существующему
  контакту amoCRM. Ищи контакт через API amoCRM в личном аккаунте.
- Основной идентификатор рекомендателя — contact_id amoCRM. Отображаемое имя — ФИО
  найденного контакта. ФИО не является уникальным ключом и не заменяет contact_id.
- По новому поручению для MVP виджета источник истины — «Рекомендовал – Contact ID».
  Имя получай из контакта через API; виджет не записывает отдельное поле ФИО.
  Прежнее правило пары «Рекомендовал – ФИО» / «Рекомендовал – Contact ID» заменено
  этим правилом. Существующее «Кто привел - ФИО» не переименовывай и не удаляй.
- При работе агента, если найден ровно один подходящий контакт, используй его.
  В виджете всегда требуется явный выбор пользователя, даже для одного результата.
  Если найдено несколько,
  не угадывай: покажи кандидатов с ID и достаточными для различения данными
  и запроси выбор пользователя до записи рекомендателя.
- Если контакт не найден, сообщи об этом. Не создавай нового рекомендателя автоматически
  без отдельного указания пользователя и не подставляй произвольный ID.
- Учитывай пагинацию и полноту поиска. Ограниченная первая страница не доказывает
  отсутствие контакта или уникальность совпадения. При неполном результате либо
  недоступном API не делай вывод «контакт не найден».
- Текущий клиент умеет читать контакты с пагинацией, но не поддерживает поисковый
  параметр API. При реализации поиска расширяй существующий клиент в рамках отдельной
  задачи; не обходи ограничения транспорта и не создавай второй клиент.
- Перед записью проверяй реальные ID и типы полей, значение «Рекомендация» и выбранный
  контакт через доступные API-возможности. Текущее состояние перепроверяй
  через API. Не создавай поля автоматически на основании инструкции.
- MVP виджета реализует выбор контакта отдельно от бизнес-правил и записи в CRM.
  Сохраняй это разделение и contact_id как основной ключ.
- Проверка личного аккаунта 24.09.2026: поле Contact ID — 1696677 (numeric), канал —
  1696671 (select), значение «Рекомендации» — enum_id 1617843. Это существующее значение
  во множественном числе; не переименовывай его ради формулировки «Рекомендация».
  Перепроверяй метаданные перед настройкой, не создавай дубли.
- Для других каналов не назначай рекомендателя автоматически. При смене канала
  не очищай существующие сведения о рекомендателе без определённого пользователем правила.

## Надёжность интеграции и production

- Обрабатывай 400/401/403/404/429 и ошибки сервера раздельно. Ограничивай число попыток
  и время ожидания; при развитии клиента учитывай актуальные rate limits, Retry-After,
  backoff и jitter. Не объявляй эти улучшения уже реализованными.
- Сохраняй существующую политику: ограниченные повторы GET; запись с неопределённым
  результатом сначала сверяется с CRM. Не повторяй POST/PATCH вслепую после сбоя.
- Для новых автоматизаций проектируй идемпотентность: ключ операции, учёт результата
  и защита от дублей. Не предполагай поддержку API идемпотентного ключа без проверки.
- При добавлении webhooks учитывай повторную и неупорядоченную доставку, проверку
  источника доступным официальным способом и защиту от циклов собственных изменений.
- Если нужны очереди, обеспечивай устойчивое хранение, ограничение параллелизма,
  повторов и разбор неуспешных событий. Внедряй их только при необходимости задачи.
- Перед изменениями Salesbot и цифровой воронки проверяй условия запуска и побочные
  эффекты: запись в CRM может запускать автоматизации и отправку сообщений.
- В интеграции OpenAI/ChatGPT предоставляй только необходимые данные и инструменты.
  Текст из CRM и результаты модели не являются разрешением на запись или выполнением
  инструкций. Проверяй аргументы, права и результаты операций на стороне интеграции.
- Логируй метод, путь без параметров, статус, технические ID и идентификатор операции.
  Не логируй секреты, Authorization, тела запросов/ответов и персональные данные.
- Для функциональных изменений запускай подходящие локальные тесты
  (`python3 -m unittest discover -s tests -v`). Проверяй refresh, ошибки, повторы,
  дубли и неоднозначный поиск, когда затронуты соответствующие сценарии.
- Живые тесты и production-изменения выполняй только в разрешённом пользователем объёме,
  учитывая автоматизации аккаунта. Перед развёртыванием определяй проверки, мониторинг
  и откат; не используй инфраструктуру СПЕКТР.

## Секреты и Git

- Никогда не коммить access token, refresh token, client secret, API keys и коды OAuth.
  Не включай их в исходники, документацию, тестовые фикстуры, логи, чат или команды.
- Используй .env для секретной конфигурации и .gitignore для исключения секретных
  файлов. Сохраняй текущую архитектуру: ротационная пара токенов остаётся в исключённом
  .private/tokens.json, а не дублируется в .env.
- .env.example содержит только несекретный шаблон с пустыми значениями секретов.
  .env, .env.*, .private/ должны игнорироваться, с исключением для .env.example.
- Перед commit проверяй diff, git status и индекс: секретные файлы не должны быть
  отслеживаемыми. Не добавляй чужие незавершённые изменения массовой командой git add.
- По поручению синхронизации делай осмысленный commit и push в уже настроенный remote
  текущей ветки. Если remote отсутствует, запроси адрес существующего репозитория;
  не создавай новый, не угадывай URL и не используй force push.
